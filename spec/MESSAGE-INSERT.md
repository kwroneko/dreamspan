# Inserting messages anywhere in the history

**Status**: Proposed, 2026-10-30. Unit 1 is implemented (ARCHITECTURE §3.7, §3.8 "Display paths"); its text in §2.2, §2.3 and §8 is obsolete there. This is the design for the owner's decision of 2026-10-30 (DESIGN §3.1 **[D]**: "Messages can be inserted anywhere in the history: written as any cast member or generated by the model at that point, in the middle of a chat as well as at its end. ST's 'Copy this message' (a duplicate right after the original) is one use of it"). Everything below is **[P]** unless it cites a **[D]**. It's a delta from master 6a353e2 (ARCHITECTURE §3.7, §3.8, §3.11, §12, §15, §16; spec/FORK-INDEPENDENCE-DELTA.md) and from reference-harness (`reference-harness`). Open questions for the owner are in §9.

## 0. Summary

- An inserted message is an ordinary slot with ordinary versions. It's marked `slots.inserted = 1` when it's created, and that never changes. Its parent is the message it was inserted below (null above the first message), so every graph invariant holds as it is: a slot's parent is one level up, the graph only grows, slots never move, and a chain holds one slot per depth.
- Where it shows is per fork: an `insert` row in `fork_overrides` places it in the fork it was inserted in. Forks made from that fork afterwards inherit the row through the lineage, like any override. No other fork shows the message, so fork independence holds by construction.
- What a fork shows becomes its **display path**: the structural path (root to tip by parent links, read by chain segment as now) with the fork's placed insertions spliced in. Message numbers, fold order, context, LCM ranges, search and every order-sensitive read use the display path and a new **position** (the index in it). `depth` stays structural: it's used for chains, segments, ancestry walks and the branch switcher, and nothing else.
- The rest goes through existing parts: deleting or undoing an insertion is `DeleteMessage` to the bin; swipes, selections, hides and stars on the inserted message are the existing overrides; a generated insertion is a swipe-shaped generation at the new slot; LCM's freshness rules for edited history decide which summaries become stale.
- Client: three registered message actions (**Insert message below**, **Insert message above** on the first message, **Duplicate**), an inline editor placed in the message stream, and a toast with **Undo**.

## 1. Delta from reference-harness and from the build

**reference-harness** has nothing to reuse for this. Its timeline (`src/timeline/store.ts`) is an append-only log per room: an edit or deletion is a marker on the stored row (`applyEdit`, `markDeleted`) and never rewrites order. Its forks (`forkSession` in `src/agent/fork.ts`, stored by `insertSessionBranch`) cut a session transcript at an index and keep the discarded span as a branch: truncate and continue, never insert. `recovery.ts` resumes and forks sessions the same way. One principle does carry over: rows stay immutable, and what changes is a marker read through an overlay. This repo's `fork_overrides` already generalizes that, and the design adds one more kind of row to it.

**This repo** (master): a fork's history is the path from the root to its tip by parent links (`pathSegments` in `db/pathSegments.ts`, `onPath` in `db/forks.ts`). A slot's position is its `depth`. Per-fork choices are `fork_overrides` rows read through `forks.lineage_json` (`effectiveOverrideSql`, `writeOverride`, `insertFork` in `db/forkState.ts`). The delta:

| Built | Changes to |

## 2. The data model

### 2.1 Alternatives considered

A chain holds one slot per depth, fixed at insert. Slots never move. Slots are shared by forks. "Between A and B" can't be made by changing B, so the options are:

1. **Re-parent B under the new slot X.** Rejected: it moves a slot (invariant "a slot and its merge parents never move", `test/schema.test.ts`, `test/chains.test.ts`), and since B is shared, every fork through B would change. That breaks fork independence, which is decided.
2. **Copy the suffix**: X under A, then copies B′, C′, … of everything after it, with their versions, overrides, events and attachments, under X in the inserting fork. Rejected:
   - It costs the length of the suffix in one writer transaction: copying 99,990 slots, plus their swipes, to insert at message 10 of a 100,000-message chat. The one-transaction rule and the measured budgets (`lcmAdoptionScale.test.ts` bounds a range write at 300 ms) rule that out.
   - Every summary after the point would get new input slots, so the whole suffix would be summarized again, which costs money.
   - Swipes belong to the message ([D], CHATS.md "Forks"), but a swipe made later on B in another fork would never reach B′.
   - Forks made from the old suffix would be cut off from it.
   - Captured requests would point at slots the fork no longer shows.
3. **Per-fork order keys** (a fractional position per slot, as an override). Rejected: every insertion writes one row per later slot (the same O(suffix) as option 2). A shared key would change every fork.
4. **Make every insertion a new fork.** Rejected: it still needs option 2 or a splice, and a branch is never a side effect (DESIGN §3.2 [D]).
5. **Store the inserted text as a state event or an annotation on A.** Rejected: it would be a second-class message, with no versions, swipes, generation, search, summary inputs or attachments.
6. **Splice overlay (chosen).** X is a real slot below A. Its place in a fork is an override, read when the path is read. Insertion is O(1) rows. Forks are independent through the existing lineage. The read pays for the insertions a fork actually has, not for the chat's length.

### 2.2 Storage

- **`slots.inserted`** (baseline edit; there's no real data yet, ARCHITECTURE §3.7). It's set to 1 by `InsertMessage` and to 0 by everything else. Trigger `slots_inserted_frozen` refuses any update of it.
  - X's `parent_slot_id` is the **anchor**, the message it was inserted below, and its `depth` is the anchor's depth plus 1.
  - Inserted above the first message, X is a root (parent null, depth 0: the existing `CHECK ((parent_slot_id IS NULL) = (depth = 0))`).
  - X's `chain_id` is assigned by `slots_chain_assigned` as for any slot. It's nearly always a later child, so it starts its own chain.
  - Its `lane_id` is the anchor's, and its `fork_id` (provenance) is the inserting fork.
- **`fork_overrides` kind `insert`:**
  - `target_id` = X, the key.
  - `slot_id` = X's anchor (null above the first message), and `slot_depth` = the anchor's depth (null with it).
  - `flag` 1 = placed in this fork; 0 = not placed (written by `CreateFork`, §2.4).
  - `value_id`, `bin_item_id` and `changeset_id` are null.
  - A new trigger `fork_overrides_insert` checks that an `insert` row names a slot of the same chat with `inserted = 1` whose parent is `slot_id`. The existing triggers already keep kind, target and fork fixed.
  - Effective value: as for every kind, the first lineage entry with a row for X, newest there (`effectiveOverrideSql('insert', fork, X)`). Lineage compaction past `LINEAGE_CAP` copies effective `insert` rows like the others, so nothing new is needed there.
- **`versions.origin` `duplicate`.** It's for a copy made by Duplicate. `source_version_id` stays null, because the invariant says a source is a version of the same slot (§3.7) and a duplicate's original is in another slot. No provenance column is added: nothing reads one, and the purge semantics of a cross-slot link would need deciding. Writer, speaker, content, `context_form`, `display_form`, `reasoning`, `macro_mode`, `frozen_macros`, `connection_id`, `model_id` and attachments (`version_attachments` rows on the same media) are copied. `rollout_id`, `usage_json`, `error_json`, flags and `version_history` are not: the copy wasn't generated at this place, and the inspector mustn't present it as if it were. A copy of a model-written version is frozen like one (writer `model`), so editing it makes a new version "edited from" it (DESIGN §3.1 [D]); §9 Q2 asks the owner about this.

### 2.3 The display path

`db/displayPath.ts` (new; readers and the writer share it, like `db/pathSegments.ts`).

- **`pathPieces(sql, chatId, forkId, tipSlotId)`** returns the fork's display path as an ordered list of pieces. A piece is either a structural run `(chain, lo, hi)` or a single inserted slot. Each piece carries its start position.
  1. Read the tip's segments with `pathSegments(…, null)`. That costs the branch points.
  2. Read the fork's effective `insert` rows with `flag = 1` whose anchor is on those segments (or is null), joined to `slots` for X's id, chain and depth. That costs one range scan of `fork_overrides_point` per lineage entry on `(fork_id, kind)`, so the fork's insertions, not the chat's length.
  3. Drop rows whose X is itself on the structural path. A fork made at or below an inserted slot has it structurally, where it already sits in its right place.
  4. Splice: walk the structural segments oldest first, and after each slot that anchors insertions, emit its **gap**.
- **The gap of slot P** is the inserted slots anchored at P, newest first by id (UUIDv7, so creation order; §3.7), each followed by its own gap. Then comes P's structural successor. "Insert message below P" therefore always puts the new message directly below P, whatever was inserted there before. Inserting at A, then at A again, then below the first one gives A, X₂, X₁, X₃, B. The gap of null (above the first message) comes before the root.
  - Rejected: ordering by override seq (lineage compaction rewrites seq), and a stored "next" pointer (it would have to change when a neighbour is inserted, which means a write per neighbour).
- **`positionOf(pieces, slot)`** and **`onDisplayPath(pieces, slot)`** (the slot's id, chain and depth): a slot is on the display path iff a structural piece covers its chain and depth, or an inserted piece is that slot.
- **Windows.** `GetPath`/`ReadPath` (`pathWindow` in `reads.ts`) read the last `limit` positions instead of the last `limit` depths: the pieces that overlap the window, then one range scan of `slots_chain` per structural piece, plus one lookup per inserted piece. `olderLeafSlotId` becomes the slot at the position before the window, which may be an inserted one. It's read in the same fork, which the reader resolves anyway (`ForkView`).
  - Cost: branch points + the fork's insertions on the path + the window.
  - Positions count from the root, so every path read reads all of the fork's insertions on the path, even those outside the window. That's the price of numbering from the start. Insertions are user actions, so there are hundreds at most, and the scale test (unit 3) pins 1,000 of them.
- **`PathEntry.position`** is new. `depth` stays on the entry for what's structural (paging internals, the branch switcher). The client numbers messages by `position`.
- **The display end** is the last piece. It's usually the tip, but it can be an inserted slot when everything structural after its anchor is deleted in the fork. The tip stays structural (`forks.tip_slot_id`, appends and `LeafMoved` as now). `GetPath` returns `tipSlotId` apart from the entries, and the client appends to that, never to "the last message shown". `ListForks`' tip text and the alternates' first words read the display end.

### 2.4 Forks, appends and tips

- **Inserting in F** writes X, its first version and an `insert` row in F, in one transaction. A fork made from F before then has a lineage bound below the row's seq, so it never sees X (fork independence [D]). A fork made afterwards inherits X wherever X's anchor is on its path.
- **A fork made at P from F, after an insertion, must end at P as F showed it** (FORK-INDEPENDENCE-DELTA §2.3). Inherited insertions in P's own gap, and in the gaps of the slots inserted after P, come after P in F, yet the new fork would splice them in after P. So `CreateFork` writes an `insert` row with `flag = 0` in the new fork for each inserted slot the new fork's own display path would show that F doesn't show at or before P (`hiddenAtFork` in `db/displayPath.ts`).
  - When P is itself an inserted slot, that also covers the older slots in its anchor's gap that come after P.
  - It also covers a slot F has structurally right below P while inheriting its `insert` row (F was made at or below an inserted slot X anchored at P). X isn't on the new fork's structural path, so the inherited row would splice it in after P. (Corrected in unit 1: the first version of this rule, "each X that F displays after P and before P's structural successor", missed it; the oracle test found it.)
  - The cost is the new fork's insertions on its path; insertions anchored further down aren't on the new fork's structural path, so they're never spliced.
  - Rejected: a rule at read time ("skip inherited insertions after the base"). It has to recompute the parent's display order at `branched_at`, recursively up the lineage, on every read.
- **Forking at an inserted slot X**: the base and tip are X, and the structural path is root, …, A, X, so appends in the new fork are X's children, by the ordinary chain rule.
- **Appending in F** is unchanged. Its parent is F's structural tip. A display end that's an inserted slot X (anchored at the tip A) stays before the new message, because the gap of A comes before A's structural successor. No append ever becomes an insertion, and no insertion moves the tip.
- **Insert at the display end** is the composer's append: the client routes "Insert message below" on the last message to `SendOrQueue` or Generate X (§4.2). The server doesn't refuse an `InsertMessage` there (a stale tab may send one), and the result displays correctly. It just stores an inserted slot where a plain one would have done.
- **`relocateLeaf`** (`db/bin.ts`) is unchanged: a tip moves to its nearest live structural ancestor. Inserted slots aren't ancestors, so they never become tips that way.
- **Branch switcher**: `ListBranches`, `BranchTip`, `siblingCount`, `reachableSlot` and `SwitchBranch` count only children with `inserted = 0`. An inserted slot is never an alternate of the message it was inserted above. A fork made at an inserted slot is listed through it like any fork.
- **`forkAt`** (`db/forkState.ts`) and every "current fork if its path holds it" use `onDisplayPath`.

## 3. What is keyed to positions or slots after the insertion point

Everything keyed by **slot or version** keeps working untouched. Everything keyed by **position or depth** moves to `position`.

### 3.1 The graph and per-fork state

### 3.4 LCM

The freshness rules for edited history are reused (ARCHITECTURE §16 *Freshness*). Edits write nothing to summaries, and staleness is derived per fork when they're read. So an insertion writes nothing to summaries either.

- **Inside a range.**
  - A summary S is stale in F when F has an effective insertion anchored at one of S's input slots other than its last. For a higher level, that means any slot its descendants cover (S's display range in F).
  - That's the rule for an edit inside the range, so the rest follows unchanged:
    - S stays usable until it's replaced.
    - A reply's planning pass writes it again over F's display range from S's first slot to its last, which now includes X.
    - No other fork is affected.
  - The reply directly after the insertion is assembled with S still in place, as after an edit of a summarized message.
- **At a seam.** X can be anchored at the last slot of S₁ while S₂ starts right after the gap. Then no summary covers X, and the layer's continuous-prefix rule would stop at the gap, leaving S₂ and everything after it raw (no-loss, but a large raw jump). So the layer walk in `db/lcmLayer.ts`, when it meets inserted slots between two consecutive candidates, treats the earlier candidate as stale for that walk (`seamStale`). Planning then rewrites S₁ over its first slot to the end of the gap, and the layer keeps S₂ meanwhile.
  - An insertion directly after the layer's cursor isn't a seam: X is raw, as any message after the cursor is.
- **Summaries that include inserted slots.** An L1's inputs are recorded in order (`summary_inputs`). Validation (`CompleteSummary`, and candidate checks in `lcmLayer.ts`) compares them with the display range from first to last in the fork concerned, instead of walking the primary-parent chain.
  - In a fork that doesn't show X, a summary whose inputs include X is inconsistent and ignored there, as today's rule says.
  - In a fork with insertions made later inside the range, the inputs are a subsequence whose missing slots are all inserted, which makes the summary stale, not inconsistent.
- **Planning and overlap.** `EnqueueSummaries`' depth-overlap check against live jobs compares positions in the job's fork, computed in its transaction from `pathPieces`. `lcmPath` (`db/lcmPath.ts`), the leaf planner's chunks and the coverage check through `summary_inputs_slot` read the display path. A job claimed before an insertion completes with its inputs, and the result is stale in F at once.
- **Client.** `NextContext`'s last covered depth and raw start, `GetLcmState`'s cursor depth and the "Summarized" and dropped labels (`CoverageRail.tsx`, `LcmBoundary.tsx`) carry slot ids and positions instead of depths.

## 4. The user flow

Every step is a visible control (owner rule: nothing behind key combinations only).

### 4.1 Entry points (registered message actions, `features/chat/registerMessageActions.tsx`)

- **Insert message below** (`message.insert-below`, order 28, between Write your own version and Branch) is in every message's "More actions" menu.
- **Insert message above** (`message.insert-above`) is only on the first displayed message (anchor null).
- **Duplicate** (`message.duplicate`) inserts a copy of the version this fork shows (its copy X′ if amended or replaced), with its speaker and attachments, directly below the message. There's no dialog. A failed or still generating version can't be duplicated: the item is disabled with the reason as its hint.

### 4.2 The insertion editor

It's a client feature, `features/chat/insertMessage/`, registered as a message-stream slot after the anchor.

- **Where it opens.** It opens inline under the anchor, in the stream, so the messages around it stay in view (a sheet on phones). There's no modal.
- **What it holds:**
  - **Speaker**: the existing `SpeakerSwitcher.tsx`, listing the cast (any cast member, the user's played cards included). It defaults to the composer's current speaker (who the user writes as) when the anchor is a character's message, else to the character who spoke last before the anchor. That's a convenience only; the user picks.
  - **The text field**: the composer's editor, with an `insert` draft (§3.1), so nothing typed is lost (§3.10).
  - **Generate as ⟨speaker⟩** (the model writes the turn) and **Insert** (writes the text as the speaker). With text in the field, Generate uses it as the direction, as the composer's Generate X does.
  - **Cancel** keeps the draft. **Discard** clears it.
- **What it tells you before you commit:**
  - The cache line, from `CacheWarmth` for a change at the anchor: "The model will re-read N messages on the next reply (cache: ~X tokens)".
  - "Before the model's history start: the next reply won't see it", when the anchor is before the stepped start.
  - "Inside summarized history: the summary is rewritten on the next reply", when an LCM summary covers the anchor (§3.4).
- **At the end of the chat** (the anchor is the display end and the tip), Insert and Generate go to the composer's paths, `SendOrQueue` and Generate X, so a running reply queues them as it queues a send.
- **Generating at the insertion point.** It's assembled like a mid-history regenerate: the fork's display path up to the anchor, then X's turn for the chosen speaker. The version streams in place, with its own stop button (DESIGN §3.1 [D]). Whether the model is also shown what comes after is §9 Q1. If it fails, it's a failed version (U08) with Retry and Retry with…, as anywhere.

### 4.3 After the insertion

- The message appears in place, briefly highlighted, and later messages renumber.
- A toast says "Message inserted" (or "Message duplicated") with **Undo**.
- Undo is `DeleteMessage` of X in this fork, which sends it to the bin: the same as **Delete** in X's own menu afterwards. A Generate is stopped first (`InterruptGenerations` on X's version). So an undone insertion stays restorable from the bin and can be purged there like any message. Restore puts it back in its gap.
- Rejected: an Undo that removes the row outright. Another fork may have been made in the meantime, and a deletion outside the bin has no purge path.

### 4.4 Tests

`e2e/insertMessage.spec.ts`: below and above, Write and Generate as two different cast members, Duplicate of a generated and of a written message, Undo from the toast, restore from the bin, the editor's cache and summary lines, renumbering, and a fork made before the insertion staying unchanged. At 1440 and 390, in light and dark, with screenshots outside the repository.

## 5. Concurrency

The writer serializes every write (`concurrency: 1`), and each op below is one transaction. What remains is how insertions interact with generations, which run outside transactions.

- **A generation is running in the same fork, at the end.**
  - The insertion goes ahead. The running request's context was fixed when it was assembled (`RecordSentContext`), so its reply doesn't contain X. That's the same as an edit made during a generation, and it carries no mark (DESIGN §3.1 [D] "No mark"); its inspector shows what it was generated from.
  - Queued messages post after that reply, at the tip, and their replies include X.
  - "Insert below" on the last message while a reply runs goes to `SendOrQueue` and queues (§4.2).
- **A generation is running at the anchor or after it** (a swipe on B): the same. B's new version was generated without X.
- **X is still generating when a later reply is assembled.** X's selected version is `generating`, so that reply's context leaves X out, as it leaves out any generating version (a mid-history swipe in progress, today). The generation at X doesn't hold the composer or the queue (the queue waits only behind its own slot, `FinishGeneration`). The editor says so while X streams: "The next reply won't include this message until it's finished."
- **Generations or queued messages in another fork G**: unaffected. G doesn't show X, and its reads, plans and summaries are its own (§3.8 "Generations and queued messages").
- **Two tabs insert at the same anchor**: both succeed. The newer one sits directly below the anchor (§2.3). Each tab's view updates through the slot events below.
- **A stale tab.** `InsertMessage` takes the anchor's row version as F shows it (`slotInFork`). It refuses with `StaleWrite` only when the anchor is no longer on F's display path or is deleted there. A neighbour inserted meanwhile is no conflict: the user asked for "below this message", and the new one still is.
- **Summary jobs** in flight over a range that contains the anchor complete with their inputs and are stale in F at once (§3.4). The next reply's planning pass rewrites them.
- **An ST re-import** of F's file meanwhile: the insertion is a local change that stops the re-import from writing F (§3.3).
- **Publishing.** The API publishes the new slot as F's `Slot` event, with its position, and the anchor's row version (taking the new seq). Other forks' tabs receive nothing to apply. That's the per-fork row version rule of §3.8, extended by the `insert` row's seq.

## 6. Structure: what is core, what is registered

- **Core** (the data model and base, PLUGINS §8 "the graph's integrity rules"):
  - `slots.inserted`, the `insert` override and its triggers.
  - `displayPath.ts`.
  - The writer op `InsertMessage`, and `CreateFork`'s flag-0 rows.
  - The position-based reads.
  - The ordering rule within a gap, which is part of what the data means and must agree between server and client.
- **Registered** (each can be overridden, disabled or added to by a plugin, including one the in-app agent writes):
  - **Server command** `message.insert` (`Commands` in `commands.ts`, registered beside `history.search` in a new `api/messages.ts`). Its input is `{ chatId, forkId, anchor, body }`, and the RPC handler dispatches through the registry, so an agent can insert messages through the same path.
  - **Client message actions** `message.insert-below`, `message.insert-above` and `message.duplicate` (`messageActions` registry).
  - **The insertion editor** as a client feature: it registers in `features/index.ts` and fills a message-stream slot.
  - **Its estimate lines** (cache, history start, summary) as entries the feature registers, so a plugin can add one.
  - **The default speaker** as a function the feature registers (`insertSpeakerDefault`).
  - **The context for a generated insertion** goes through the registered assembler stages unchanged. "Show what comes after" (§9 Q1) would be one more registered stage (`assembler/following.ts`, id `history.following`).
  - **LCM's seam handling** sits in the layer walk's candidate check. The re-summarizing it causes goes through the registered `maintenancePlanners`.

## 7. Write and read operations (`db/ops.ts`)

- **`InsertMessage`** (writer, `db/insertWrites.ts`, one synchronous transaction). Payload:
  - `userId`, `chatId`, `forkId`
  - `anchorSlotId: SlotId | null`
  - `expectedRowVersion` of the anchor as F shows it
  - `body`, one of:
    - `Write { speaker, content, draft: { id, rowVersion, session } }`
    - `Generate { speaker, direction?, draft? }`
    - `Duplicate { versionId }`, the version F shows at the anchor's message being copied (it may differ from the anchor)

  The transaction does this, in order:
  1. Check ownership and liveness (`NotFound`): the chat, the fork, the speaker as a cast member (`CastCards`'s rule), and the version to duplicate.
  2. Check that the anchor is on F's display path and not deleted in F (`StaleWrite`).
  3. Insert the version (status `complete`, or `generating` for Generate, writer `model` with origin `generated`), then the slot (`inserted = 1`, parent = anchor, `fork_id` = F), then the attachments for Duplicate.
  4. Write the `insert` override (`writeOverride`, next `state_seq`).
  5. Commit the draft (§3.10 rules).
  6. Mark F chatted in. Inserting adds a message, which is what "chatted in" means (§3.8, owner 2026-10-27), so F becomes current.

  It returns the slot as F shows it, its position, and for Generate the version to start. The API then calls `Generations.start({ slotId, versionId, forkId })` outside the transaction, as a swipe does.
- **`CreateFork`**: plus the flag-0 `insert` rows of §2.4, in its transaction.
- **Reads**: `GetPath`, `ReadPath`, `ListForks`, `ListBranches`, `StateEventsAt`, `AssembleContext`, `CacheWarmth`, `PlanSummaries`, `GetLcmState` and `GetLcmCoverage` take positions through `pathPieces`. `ListVersions` and `GetSlot` are unchanged.

## 9. Open questions for the owner

**Q1. When the model generates an inserted message, does it see what comes after?**
- *Situation:* an inserted message sits between two that already exist. A generation that sees only what comes before (as a mid-history regenerate does today) often writes something the next message contradicts. DESIGN §3.1 already proposes, unconfirmed, an option for regenerating mid-history: "write a replacement consistent with what comes after".
- *Options:* (a) never, like a regenerate today; (b) a checkbox in the insertion editor, "Show the model what comes after", off by default; (c) the same checkbox, on by default for insertions.
- *Consequences:* (a) is the simplest, and the cache prefix up to the anchor is reused. (b) and (c) send the following messages, up to a budget, after an instruction to write the message that goes between. That's a new registered assembler stage, and the request shares no cached prefix beyond the anchor.
- *Recommendation:* (b) in the first build, with the stage registered, so the default can be flipped later without code.

**Q2. Is a duplicate of a model-written message still model-written?**
- *Situation:* DESIGN §3.1 [D]: editing a generated version makes a new version ("edited from"), while editing a version the user wrote amends it in place. A duplicate is a copy the user asked for, of text the model wrote. How the immutable model is presented is still open (DESIGN §3.1 [O]).
- *Options:* (a) it keeps the original's writer: a duplicated reply is frozen, and editing it adds a version; (b) it becomes the user's: editing amends it in place, with undo history.
- *Consequences:* (a) keeps "who wrote this text" true, and the picker shows a model message. (b) is what ST's copy-then-edit feels like, but labels model text as the user's.
- *Recommendation:* (a). The design above assumes it, and (b) is a one-line change in `InsertMessage` if the owner prefers it.

Decided here and not asked, since they follow from decided rules:
- An insertion counts as chatting in the fork ("adding a message", §3.8).
- Undo goes through the bin.
- Inserting at the end is the composer's append.
- The newest insertion goes directly below the message it was inserted below.
- An insertion inside summarized history follows the edit rule: the summary is rewritten on the next reply.
