This inventory supplies discussion cases, not a proposed design or approval of the existing UI.

**Reading key.** D = [DESIGN](DESIGN.md); A = [ARCHITECTURE](../ARCHITECTURE.md). [D], [P], [O] retain DESIGN's decided/proposed/open meanings. Implemented behavior in A or code does not promote a proposal to a decision. Scenarios are synthetic: **action → expectation → actual result**. Rows about unbuilt features explicitly describe a future exposure or a missing control.

**Evidence baseline.** “Today” means this branch's starting HEAD, `443f890`. Components below are in `packages/client/src/features/`, unless a different path is given. The implementation was read, including the calls in `chat/session.ts`; behavior that the client does not explain was checked against A and, where necessary, server code. [ST-GRIPES](ST-GRIPES.md) supplies the checklist, particularly C, D, F, G, I and J; its rankings and suggested builds are not adopted here. ST is discussed only as an import source, never as a comparator for this model's UX.

## Open questions for the owner

These ask about presentation and expectations; they do not reopen decided preservation, explicit-fork or non-loss rules.

**Messages and provenance**

- What should Edit/Save tell the user when it will create a version, versus amend their existing text?
- How should the user recover pre-amend text and earlier drafting text, including after a commit?
- What should “edited from #N” identify, and how should that identification survive deletion and differ from message numbers?
- What should the user be told about unchanged later replies after selecting, editing or regenerating a mid-chat version?
- How should generated persona turns, one-off model choices, concurrent streams, Continue and failed/refused versions communicate their different effects?
- How should hiding a version from navigation be distinguished from hiding its message from the model?

**Branches, positions and state**

- What should a branch promise about shared earlier messages, version selections, summaries and mutable library refs?
- How should the user know the exact position a panel change affects, especially while scrolling old messages or viewing an inactive path?
- What should creating, naming, switching, restoring and deleting a branch mean in the presence of nested forks and another open tab?
- How should state history, version-attached effects and any apply-to-all-branches action expose the identities and scope they act on?
- How should chat-wide settings, branch-local state, inherited defaults and composer choices be distinguished?
- What user-visible distinction will separate peer chats, alternate branches and future concurrent threads/merges?

**Entities and scope**

- What should “Only in this chat” promise about past positions and other branches when the override is a moving ref?
- How should Everywhere explain followers, pins, conflicts and the conservative used-by count?
- How should originals, variants, local overrides, saved revisions and library/in-chat names be identified and navigated?
- How should note ownership, activation, positional content revisions, placement and separate Save actions be made understandable together?
- How should users recognize upstream changes that reached their local edits, versus changes still waiting for resolution?

**Deletion and recovery**

- How should users distinguish deleting a version, a message, a whole subtree and a chat before using the fast delete action?
- What should restoration communicate when a chat continued since deletion or its attached state becomes active again?
- How should permanent removal, invisible placeholders, retained summary facts and capacity eviction be explained?
- Where should users expect to find discarded, displaced, offline and queued text, and what does recovering each kind do?

**Context and summaries**

- How should Hidden, Out of context, Summarized, template text and historical context differ from the request the next send will use?
- What should users expect after editing covered history while stale or protected manual/imported summaries still stand in for it?
- How should shared summary scope, summary revision selection and pending replacement choices be communicated across forks?
- Where should re-summarize/retry be discovered, and how should next-reply timing, failures, cache waiting and backfill spending be conveyed?
- How should adopting an imported summary or starting afresh communicate the exact visibility and representation change?

**Imports, drafts and pending sends**

- What should re-import preview/report about merges, new swipes, source edits that fork, preserved local choices and state changes needing new messages?
- What should “saved” mean on each surface, including drafts, browser-only text, revisions, immediate avatar/name writes, exports and transient queue edits?
- How should users understand which branch, speaker, selected reply slot/version and one-turn direction a queued send will use?
